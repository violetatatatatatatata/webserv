================================================================================
WEBSERV - FIXES PARA PASAR EL TESTER DE 42
================================================================================

Este archivo resume todos los cambios realizados para que el binario tester
de 42 (./tester http://localhost:8080) pase con exit code 0.

================================================================================
FIX 1 — Decodificación correcta de chunked transfer encoding
         Archivo: srcs/http/Request.cpp — método parse()
================================================================================

PROBLEMA:
  El método parse() usaba getline() para extraer el body, lo que concatenaba
  línea a línea el wire format chunked completo (incluyendo tamaños de chunk
  como "186a0", "0", etc.). Para un body de 100MB, el resultado tenía ~24420
  bytes extra respecto al tamaño real. El cgi_tester detectaba la discrepancia
  y devolvía error "bad cgi returned size body".

SOLUCIÓN:
  Buscar el final de los headers (\r\n\r\n) en el buffer raw, luego decodificar
  el formato chunked correctamente: leer tamaño en hex → saltar \r\n → copiar
  exactamente esos bytes → repetir hasta chunk de tamaño 0.

================================================================================
FIX 2 — CONTENT_LENGTH vacío en peticiones chunked al CGI
         Archivo: srcs/http/CGIHandler.cpp — buildEnv()
================================================================================

PROBLEMA:
  Las peticiones chunked no llevan cabecera Content-Length. El código hacía
  directamente env.push_back("CONTENT_LENGTH=" + getHeader("Content-Length")),
  que producía "CONTENT_LENGTH=" (vacío). El cgi_tester leía 0 bytes de stdin.

SOLUCIÓN:
  Si Content-Length está vacío, usar el tamaño del body ya decodificado.

================================================================================
FIX 3 — Cabeceras HTTP no se pasaban al CGI como variables HTTP_*
         Archivos: srcs/http/CGIHandler.cpp — buildEnv()
                   inc/http/Request.hpp + srcs/http/Request.cpp — getHeaders()
================================================================================

PROBLEMA:
  El test "special headers" enviaba X-Secret-Header-For-Test: 1. El cgi_tester
  busca la variable de entorno HTTP_X_SECRET_HEADER_FOR_TEST; si vale "1",
  reemplaza todos los bytes del body con el carácter '1'. El servidor no pasaba
  ninguna cabecera HTTP al entorno del CGI, así que el body no se transformaba
  y el test fallaba con "bad cgi returned body content".

SOLUCIÓN:
  Añadir getHeaders() a Request para exponer el map completo. En buildEnv(),
  iterar por todas las cabeceras y añadirlas al entorno con formato CGI:
  guiones → guiones bajos, todo en mayúsculas, prefijo "HTTP_".
  Content-Type se añade además como CONTENT_TYPE (sin prefijo HTTP_).

================================================================================
FIX 4 — Script CGI inexistente devolvía 404 en lugar de 200
         Archivo: srcs/http/CGIHandler.cpp — handleRequest()
================================================================================

PROBLEMA:
  El test POST /directory/youpla.bla referencia un script que no existe.
  handleRequest() comprobaba la existencia del fichero script y devolvía 404
  si no lo encontraba. Pero el binario cgi_tester gestiona internamente los
  scripts inexistentes y devuelve 200 con body vacío.

SOLUCIÓN:
  Comprobar solo que el BINARIO CGI (cgi_tester) existe y es ejecutable,
  no el fichero script.

CÓDIGO ANTES:
  - int res = HttpHandler::isFileInError(X_OK, _scriptPath);

CÓDIGO DESPUÉS:
  + int res = HttpHandler::isFileInError(X_OK, _binPath);

================================================================================
FIX 5 — POST en /post_body devolvía 405 Method Not Allowed
         Archivos: srcs/http/StaticHandler.cpp, inc/http/StaticHandler.hpp
================================================================================

PROBLEMA:
  isMethodAuthorized() tenía `if (_request.getMethod() == "POST") return false;`
  que bloqueaba todos los POST aunque la location los permitiera explícitamente.
  Además, handleRequest() solo despachaba GET y DELETE; POST no tenía handler.

SOLUCIÓN:
  Eliminar el bloqueo incondicional de POST. Dejar que el bucle sobre los
  métodos permitidos de la location decida. Añadir handlePOST() que devuelve
  200 OK con body vacío.


================================================================================
FIX 6 — Límite de body size no se aplicaba a peticiones chunked
         Archivo: srcs/core/Cluster.cpp — processHttpRequest()
================================================================================

PROBLEMA:
  La comprobación de client_max_body_size usaba contentLength, extraído de la
  cabecera Content-Length. Para peticiones chunked esa cabecera no existe →
  contentLength = 0 → el límite nunca se disparaba. El test POST /post_body
  con 200 bytes (límite 100) no devolvía 413.

SOLUCIÓN:
  Para chunked, usar el tamaño real del body ya decodificado, que se obtiene
  de request.getBody().size().


================================================================================
FIX 7 — O(n²) en detección de fin de body chunked [CRÍTICO DE RENDIMIENTO]
         Archivos: srcs/core/Client.cpp, inc/core/Client.hpp
================================================================================

PROBLEMA:
  processChunkedBody() buscaba el marcador de fin "0\r\n\r\n" escaneando el
  buffer COMPLETO desde el principio en CADA llamada a recv():

      void Client::processChunkedBody() {
          if (_requestBuffer.find("0\r\n\r\n") != std::string::npos)
              _parseState = READY;
      }

  Para un body de 100MB recibido en bloques de 65536 bytes:
    - 1526 llamadas a recv()
    - La i-ésima llamada escanea i × 65536 bytes
    - Total: ~76GB de escaneos de string por conexión

  Con 20 conexiones concurrentes de 100MB en el test final:
    - 20 × 76GB ≈ 1.5TB de operaciones de búsqueda
    - El servidor se quedaba al 98% de CPU durante 12+ minutos sin avanzar

SOLUCIÓN:
  Añadir _chunkedSearchPos al estado del cliente para recordar hasta dónde se
  buscó la última vez. En cada llamada, buscar solo desde ese punto menos
  4 bytes de solapamiento (por si "0\r\n\r\n" quedara partido entre dos recv).



================================================================================
FIX 8 — Timeout de CGI demasiado corto para cargas concurrentes
         Archivo: srcs/core/Cluster.cpp
================================================================================

PROBLEMA:
  Con #define TIMEOUT 4, los 20 procesos CGI concurrentes del test final
  (cada uno procesando 100MB) tardaban más de 4 segundos por la contención
  de CPU y memoria. El servidor los mataba con SIGKILL y devolvía 504 a todos.


================================================================================
FIX 9 — Buffer de recv demasiado pequeño
         Archivo: srcs/core/Cluster.cpp — handleClientData()
================================================================================

PROBLEMA:
  Con un buffer de 10000 bytes se necesitaban ~10.000 llamadas a recv() para
  recibir 100MB por conexión, y con 20 conexiones concurrentes, 200.000 syscalls
  solo para la recepción. También aumentaba el número de veces que se ejecutaba
  processChunkedBody() (y por tanto el número de búsquedas en el buffer).

================================================================================
OTROS CAMBIOS MENORES
================================================================================

--- srcs/core/Cluster.cpp: buffer de lectura del pipe CGI ---
  El buffer de read() sobre el pipe del CGI también era pequeño (1024 bytes).
  Aumentado a 65536 para leer la salida del CGI en menos iteraciones.

  - char buf[1024];
  + char buf[65536];

--- srcs/core/Cluster.cpp: manejo de TCP half-close durante CGI ---
  Si el cliente enviaba FIN (half-close TCP) mientras el CGI aún procesaba,
  el servidor cerraba la conexión y el CGI quedaba huérfano sin poder enviar
  respuesta. Añadido hasPendingCGI() para detectar este caso y solo marcar
  el fd como inactivo sin cerrarlo todavía.

--- srcs/core/Cluster.cpp: parsing de cabeceras CGI en la respuesta ---
  El CGI devuelve sus propias cabeceras (Status:, Content-Type:) antes del body,
  separadas por \r\n\r\n o \n\n. El código anterior ignoraba esas cabeceras y
  devolvía el output completo como body. Añadido parser para extraer Status y
  Content-Type del output del CGI antes de construir la respuesta HTTP.

--- .config_files/tester.config: configuración corregida ---
  El fichero de configuración tenía varios errores:
  - client_max_body_size del servidor era 100 (bloqueaba los POST de 100MB)
    → cambiado a 200000000 (200MB)
  - /post_body no tenía client_max_body_size propio → añadido 100
  - /directory/ solo permitía GET → añadido POST
  - /directory/ no tenía cgi_ext ni cgi_path → añadidos para .bla

================================================================================
RESULTADO FINAL
================================================================================

Con todos estos cambios el tester pasa completamente (exit code 0, imprime
"Terminado") en menos de 10 minutos en hardware normal.

Tests que pasan:
  - GET, POST, HEAD en /
  - GET de ficheros existentes e inexistentes (404) en /directory/
  - POST a CGI con body de 100MB (chunked)
  - POST a CGI con script inexistente → 200 OK
  - POST a CGI con cabeceras especiales (HTTP_X_SECRET_HEADER_FOR_TEST)
  - POST /post_body: tamaño dentro del límite → 200; fuera → 413
  - 5 workers × 15 GET concurrentes
  - 20 workers × 5000 GET concurrentes
  - 128 workers × 50 GET concurrentes
  - 20 workers × 5 POST de 100MB concurrentes al CGI
